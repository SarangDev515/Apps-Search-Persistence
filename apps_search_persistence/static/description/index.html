Search → upgrade → return to your results

Use the existing Odoo Upgrade action. The module keeps the standard registry rebuild and full browser refresh.

3. Click Upgrade

5. Return to Apps

04 / WHAT IS KEPT

A native state snapshot—not an input-field trick

The extension exports Odoo’s full search model and restores it through the supported view loading path.

05 / INSTALL & UPDATE

Load the code, then load the browser assets

No paid addons, external libraries or third-party services are required. The only declared module dependency is web.

1

Place the addon in extra_addons

Extract the ZIP so it contains one apps_search_persistence directory. Ensure extra_addons is in your Odoo addons_path.

2

Restart Odoo

A restart imports the Python method extension. Replacing files on disk alone does not update the running process.

3

Update the Apps list and install

Enable developer mode, update the Apps list, remove the default Apps filter, search Apps Search Persistence and install it.

4

For an existing installation, upgrade this extension

Upgrade Apps Search Persistence in the intended database. The first upgrade may still execute older browser assets.

5

Hard-refresh and use Apps normally

Press Ctrl+Shift+R. Open Apps, commit a search facet, choose List or Kanban and use the existing Upgrade action.

06 / TECHNICAL FLOW

Why the screen stays in Apps

The inspected Odoo 19 upgrade path normally returns a URL action to /odoo when no configuration todo remains. That home navigation can open Discuss.

Backend

The method extension calls the original button_immediate_upgrade(). It converts only the default /odoo self-redirect into a native reload targeting the Apps action and menu; existing eligible reload destinations are corrected too. Explicitly different source actions and configuration actions are left alone.

Frontend

Native RPC events identify the request and its successful reload response. A one-shot, tab-local handoff stores the native search state and selected view. The registered reload wrapper preserves the Apps route and delegates the full reload to Odoo.

After refresh

The service consumes the handoff and supplies globalState. Odoo’s WithSearch loads SearchModel state before the view queries its records.

07 / SAFETY & LIMITATIONS

Predictable behavior beyond the happy path

The extension does not edit Odoo core files, replace Upgrade buttons, suppress registry reloads or directly change module records.

  • The handoff is scoped to the database, user and exact destination; expires after ten minutes; and is consumed once.
  • Ordinary menu navigation does not save an upgrade handoff. Stale, malformed or mismatched data is rejected.
  • Storage is sessionStorage, not shared localStorage. Duplicated tabs may inherit an initial copy according to browser behavior, but later changes remain independent.
  • Installation and uninstallation methods are unchanged. The progress overlay is specific to immediate upgrades.
  • Commit a search facet before upgrading. Uncommitted autocomplete text is not part of the preserved state.
  • Blocked sessionStorage prevents search-state restoration. The backend still targets Apps for eligible default upgrade redirects.
  • Opening an app’s detail form is outside the List/Kanban search handoff. Custom upgrade actions and third-party frontend overrides require compatibility testing.
  • Name lookup uses loaded module records, with an asynchronous read of missing selected names. If lookup fails, the heading uses “Selected application”.
  • Immediate upgrades with no explicit source action return to Apps; an explicitly different source action retains its standard destination.
08 / VERIFY IN YOUR DATABASE

A practical acceptance checklist

Completed checks are distinguished from browser behavior that has not yet been verified.

Completed validation

  • Initial installation on a clean Odoo 19 database.
  • Actual backend immediate upgrade returned an Apps reload destination after correction.
  • 16 mocked search-state regression scenarios.
  • Progress lifecycle and single/multiple-name service tests.
  • JavaScript syntax and SCSS compilation.

Live browser checks still needed

  • Search, filters, matching results and mode after List/Kanban upgrades.
  • Partial terms, multiple results and sequential upgrades.
  • Navigation away and return without stale restoration.
  • Centered overlay, blur, focus and application names.
  • Normal installation/uninstallation and frontend console errors.

Automated service tests do not prove live UI success. See the included README.md and TEST_RESULTS.md for setup, implementation details and the recorded validation evidence.
